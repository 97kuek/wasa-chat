1. **測っていないことは書かない。** 推測や見立ては[01-設計方針.md](01-設計方針.md)側に置きます

| 常時接続（メンション方式）の費用 | **月8,000円規模**（無料枠は1か月259万秒中18万秒＝**約7%**） |
| スラッシュコマンド（HTTP Interactions） | **¥0**（`min-instances=0` のまま） |
| Discordの応答制限 | **3秒**（回答は10〜30秒 → deferredで越える） |
| 追いかけて書き換える猶予 | 15分（こちらは5分で諦める） |
| 1メッセージの上限 | 2000字 |
| Goテスト | 11パッケージ成功（`discord` を追加） |

**読み取れたこと**

- **メンションは費用と両立しない。** Gatewayの常時接続が要り、心拍を返し続けるため
  CPUを常に割り当てる必要がある。無料枠は1か月の約7%しかカバーしない
- スラッシュコマンドは呼ばれたときだけHTTPで届くので、ゼロスケールのまま動く。
  **使い勝手で劣る点は見当たらない**（引数の補完が効き、雑談で暴発しない）
- **出典の保証はDiscordでも守れる。** 画面のカードが無いぶん、サーバーが文字列として
  組み立てて添える。モデルが書けるのは資料番号だけ、という性質は変わらない
- 2000字で切るときは**本文を削って出典を残す**。逆にすると、長い回答ほど根拠が
  分からなくなる

**判断を変えた点**

- docs/01 §7 の設置形態を更新した。**「Discordに置く」ことへの反論は、
  「Discordから呼べる」ことへの反論ではない。** 知識の正本は索引とWikiにあり、
  代のDiscordが消えても索引もWebアプリも残る
- ⚠️ **参照範囲はチャンネルごとに分けない**（2026-09-13に人間が判断）。まず全範囲で
  動かす。非公開Wikiの内容がチャンネルへ出ることはPMが承認済み
- ⚠️ **失効の手段が2か所になった**（docs/09 A-7）。Wikiのアカウントを止めるだけでは
  Discord経由を止められない

## 測定の型

新しい測定を足すときは、次の4つを必ず書いてください。

数字だけを貼っても、あとから読む人には何のために測ったのか分かりません。
逆に、**「何を判断したか」まで書いてあれば、同じ検討を繰り返さずに済みます。**

1. **日付 / 対象データの規模 / 再現コマンド**
   - 再現コマンドが無い数字は、あとで確かめようがありません
2. **数字**（表の形で）
3. **読み取れたこと** — その数字から何を判断したか
4. **判断を変えた点** — 設計方針のどこを書き換えたか

なお、**変えなかった場合も「変えなかった」と書いてください。**
測ったうえで維持したのか、単に測っていないのかが区別できなくなるためです。

分量が増えてきたら、**「いまの数字」と「確定した判断」を上に保ったまま、
個々の記録を数行へ圧縮**してください（2026-08-09に一度実施）。
詳細はGit履歴に残るので、消しても失われません。

## M63. Discordの検索APIと実サーバーの実測（2026-09-13）

WASA42代のサーバー（ボットを招待済み）で実際に叩いて確かめた。

**数字**

| 測ったこと | 結果 |
|---|---|
| `GET /guilds/{id}/messages/search` をBOTトークンで | **HTTP 200**（`total_results` 165） |
| `channel_id` を明示した絞り込み | 効く（指定外のチャンネルは返らない） |
| 公開チャンネル43件を1つのURLで指定 | **HTTP 200**（URL 1,359字） |
| テキスト系チャンネル | 48件（公開43 / 非公開5） |
| 名前が重複しているチャンネル | **「全般」11件・「進捗」6件・「配車関係」2件** |

**読み取れたこと**

1. **「検索APIはユーザーアカウント専用」は誤り。** 2026-09-13時点でBOTトークンで
   叩ける。全チャンネルを巡回する実装は不要だった。
2. チャンネル名の重複が想定よりはるかに多い。`#全般` が11個並ぶと、要約の見出しも
   補完の候補も**どの班の話か分からない**。
3. 非公開の5件が「議事録」「荷重試験」「代表資料・アンケート」「全組試験・回転試験」
   「google-form」。**引き継ぎとして価値が高いものほど非公開**という並びになっている。

**追測（同日、権限変更後）**

PMがDiscord側の権限を変更した。

| 測ったこと | 変更前 | 変更後 |
|---|---|---|
| 公開 / 非公開 | 43 / 5 | **48 / 0** |
| 名前の重複 | 全般11・進捗6・配車関係2 | 全般11・進捗6・議事録2・配車関係2 |
| カテゴリを足した後に残る重複 | — | **なし**（21件すべて解消） |
| カテゴリに属さない公開チャンネル | — | 2件（素の名前のまま） |
| 48チャンネル指定の検索 | — | HTTP 200（URL 1,532字） |

⚠️ **非公開が0になったため、「公開チャンネルだけ」という絞り込みはこのサーバーでは
何も除外しない。** WASA Chatにログインできる人は、Discordの全チャンネルの内容へ
到達できる状態になった（docs/09 A-12）。

**過学習していないことの確認**

カテゴリ構成はサーバーごとに違う。実装が持っている規則は
「**名前が重複したものにだけカテゴリを足す**」だけで、班名やカテゴリ名は
コードに入っていない。カテゴリが無いサーバー・重複が無いサーバーでは何もしない
（`qualifyNames` とそのテスト）。

**判断を変えた点**

- 巡回方式をやめ、公式の検索APIを使う実装にした（`internal/discord/search.go`）
- 名前が重複するチャンネルには**カテゴリ名を足す**（「駆動班 / 全般」）。
  重複していない名前はそのまま（全部に足すと冗長になるだけ）
- 43件を1リクエストで指定できるので、チャンネルごとに分ける必要はない

## M64. Discord検索の語の渡し方（2026-09-13）

本番で「Discordの公開チャンネルを検索しました」と表示しながら、**1件も読んで
いなかった**。原因を実サーバー（WASA42代・公開48チャンネル）で測った。

**数字**

| 検索語 | ヒット数 |
|---|---:|
| 質問文まるごと（`Discordにはどんな内容が書かれている？チャンネル名とか色々教えて`） | **0** |
| `翼型` | 27 |
| `荷重試験` | 21 |
| `申請` | 16 |
| `チャンネル` | 7 |
| `申請方法` | 1 |
| `荷重試験 申請` | **1** |
| `チャンネル 名` | **0** |

**読み取れたこと**

1. `GET /guilds/{id}/messages/search` の `content` は**語の一致**で探す。
   文をまるごと渡すと必ず0件になる。**利用者には「検索しました」と出るので、
   壊れていることが分からない。**
2. **語を複数渡すとAND条件**になり、急に当たらなくなる。
   「荷重試験」21件が「荷重試験 申請」で1件。
3. 長い複合語も当たりにくい。「申請」16件が「申請方法」1件。

**判断を変えた点**

- 質問文をそのまま渡すのをやめ、`internal/discord/query.go` で語を1つだけ選ぶ。
  選ぶのは**いちばん長い塊**（ひらがなの連なりを境目にして区切り、助詞・語尾を落とす）
- **1語だけにする。** 精度はヒットの前後（`around`）とモデルの読み分けに任せ、
  ここでは取りこぼさないことを優先する
- 語が取れない質問（「教えてください」だけ等）は**検索そのものを行わない**。
  投げても0件なので、Discordへのリクエストを1回節約する
- 形態素解析は入れない。辞書と依存が増えるわりに、ここで要るのは助詞と疑問文の
  型を落とす程度。足りなければ測ってから足す

## M65. Discord検索を語ごとに分ける（2026-09-13）

「検索しているのにチャット履歴を見ている感じがしない」という指摘を受けて測った。

**数字**（WASA42代・公開48チャンネル）

| 質問 | 投げ方 | 取得 |
|---|---|---:|
| 荷重試験の申請方法を教えてください | 1クエリ「荷重試験 申請」（AND） | **1件** |
| 〃 | 「荷重試験」 | 21件 |
| 〃 | 「申請」 | 16件 |
| 〃 | 「申請方法」 | 1件 |
| 鳥コンアンケートについて教えて | 「アンケート」 | 15件 |
| 〃 | 「鳥コン」 | 25件（全体42件） |

**読み取れたこと**

語をANDで1クエリにまとめると1件まで落ちるが、**語ごとに分けて投げれば
21+16+1 = 最大38件**（重複除く）まで広がる。検索は1回1リクエストなので、
3回投げても負荷は軽い。

**判断を変えた点**

- 1語だけ選ぶのをやめ、**特徴的な順に最大3語**を別々のクエリで投げて束ねる
- 前後を取りに行くヒットを 5 → **12件**へ。前後5件ずつ付くので、
  最大 12×11 = 132件の発言が回答の材料になる
- 何の語で探したかは画面の説明文に全部出す（「荷重試験」「申請」…）

## M66. Office形式の取り込み（2026-09-13）

共有ドライブの取り込みで、PDFとGoogle形式しか読めておらず、**257件を捨てていた**。

**数字**

| | 取り込み前 | 取り込み後 |
|---|---:|---:|
| 索引のページ | 801 | **961** |
| 共有ドライブの件数 | 155 | **315** |
| 共有ドライブの文字数 | 584,124 | **865,758** |
| 目次の固定部分 | 34,689字 | 34,689字（変わらず） |
| 目次の共有ドライブ節 | 21,023字 | 44,031字（「+」でオンのときだけ） |

内訳は 文書89（Word + Googleドキュメント）／表52（Excel + スプレッドシート）／
スライド20（PowerPoint）／PDF 154。

**読み取れたこと**

1. Drive側で変換するには**書き込み権限が要る**（Googleドキュメントへコピーする必要が
   あるため）。読み取り専用を保ちたいので、ZIP+XMLを手元で開くほうを選んだ。
2. **Excelは全シートを読む必要がある。** CSVエクスポートは先頭シートだけで、
   複数シートの表は取りこぼす。数式ではなく計算結果を読む（data_only）。
3. **Wordは表を拾う必要がある。** 段落だけだと諸元表が丸ごと消える。
4. 固定プレフィックスが 34,689字のまま変わっていない。Driveの節を分けておいた
   効果が、ファイルが2倍になっても保たれている（M63の判断の裏づけ）。

**判断を変えた点**

- `--only <出所>` を足した。取り出し方を変えただけなのに全部取り直すと、
  公式サイトの500ページで11分かかる。Driveだけなら数分で済む
- `publish` は手元に無いファイルを飛ばすようにした。`--only` では基準
  （sources.json）を進めないので、そのまま公開しようとして落ちていた
