# WASA Chat データ検索とルール

> 引き継ぎ資料 02（全10文書）— 資料を検索可能にし、コードで結果を保証する仕組み<br>
> [前: 01-設計方針](01-設計方針.md)｜[次: 03-プロンプト](03-プロンプト.md)

モデルの判断だけで処理してしまうと、それだけでトークン数を消費してしまいます。

ルールベースで処理できること（例えば全角を半角に直すなど）は、コードで機械的に処理した方が、
LLMと違って同じ結果を保証できますし、トークン数の無駄遣い削減に繋がります。

そこで、この文書では、資料の索引化と検索からAPI入力の検証まで、
WASA Chatがコードで決定的に処理する規則をまとめます。

## 保証の強さ

本題に入る前に、ひとつだけ気をつけてほしいことがあります。

WASA Chatには「必ずそうなるもの」と「そうなってほしいもの」が混ざっています。
この2つを同じ強さのものとして説明してしまうと、**守られていない前提の上に機能を足す**
ことになり、あとで痛い目を見ます。強さは3段階あると考えてください。

**1. コードの保証（必ずそうなる）**

コードがそう書いてあるので、モデルが何を返そうと結果は変わりません。

- 入力上限と許可値
- 参照範囲外ページの除外
- 出典カードの組み立て
- 実在タイトル・節IDの照合
- 型番の正規化一致
- 履歴件数と会話文脈の上限

**2. 緩和策（そうなりやすいだけ）**

- system規則による、資料外補完・指示上書きの抑制
- ただし、モデルが必ず従う保証ではありません

**3. 社会的な抑止（人の行動に期待するもの）**

- アシスタント作成者名の表示
- 他人の設定を直接編集させず、閲覧と複製だけにすること

## 索引生成

Wiki、公式サイト、フライトシミュレータガイドの本文を、検索できる形へ整えるところです。

正本は`ingest/build_index.py`です。ここでの判断ミスは後段すべてに響くので、
実データを見て決めた部分が多くあります。

**対象にするもの**

- MediaWiki標準名前空間の実記事
- 公式サイトの固定ページと投稿
- フライトシミュレータガイドの公開ページ
- リダイレクトは本文にせず、転送先の別名として保持します

**除外するもの**

短いページを機械的に切り捨てないのがポイントです。98字しかない「作業場移転履歴」に、
移転年・移転先・理由が完結して書かれていました。**短い＝価値がない、は誤りでした。**

- 20字未満だけを実質的に空とみなし、チャンク化しません
- 120字未満はスタブ表示にしますが、20字以上なら検索対象から外しません

**チャンク（検索の単位）**

- 目標1,200字
- 最大2,500字
- 末尾が200字未満なら、最大値を超えない範囲で直前へ吸収します
- 最上位見出しをまたぎません
- パンくずは、チャンク内の全節の共通接頭辞から作ります

パンくずを先頭節から作ると嘘になります。また、見出しをまたがない規則を厳格にしすぎると
見出しだけの細切れが大量に出るため、小さいグループ同士の結合は許しています。

**個人情報**

マスキングはwikitextをパースする**前**に行います。後だと`[[Mailto:...]]`が
内部リンク扱いになり、`links`配列に取り残されるためです。

- 生年月日を`［生年月日］`へ置き換えます
- 個人用メールを置き換えます
- 業務上の申請先・共有連絡先は残します
- 氏名、役職、区分は検索要件があるため残します

業務用と個人用を分けているのには理由があります。一律にマスクしていたとき、
荷重試験の申請先という**業務上必要な窓口アドレスまで消えていました**（M5）。
「個人情報だから伏せる」という粒度では粗すぎたということです。

**区分（班）**

- `TEAM_RULES`を正本とします
- 代まとめ・人物ページを先に弾きます
- タイトルを優先し、無ければ本文冒頭400字で補います

人物ページを先に弾くのは、本文に「空力設計」と書かれた名簿ページが空力班に混ざり、
班フィルタが信用できなくなっていたためです。

**年代**

- `last_edited`を、本文の鮮度として使いません
- 本文の西暦と20〜49代を、チャンク単位で抽出します
- `N代 = 1984 + N年大会`で西暦へ対応させます

この換算式は、公式サイトの歴史ページとWiki側の記述の全代で、例外なく一致しました。
モデルに推測させる必要はありません。

## ページ・節の選択

質問から、どの資料を読むかを決めるところです。

正本は`backend/internal/pipeline/pipeline.go`です。基本はLLMに選ばせますが、
**LLMが失敗しても正解が落ちないように、コード側で候補を足しています。**

**ページの選択**

- モデル候補は最大4件です
- `index.Resolve`で、実在タイトルまたは一意な別名だけへ解決します
- 架空タイトル、曖昧な部分一致、節名を落とします
- 質問中の実在タイトルを、型番候補と合わせて最大2件までモデル候補より先に加えます
- `40th`と`40代`は同一視し、分野名と世代の両方が合うページを優先します
- 3文字以下の英数字タイトルは、単語完全一致だけを認めます（`PM`が`RPM`に当たるのを防ぐため）
- 0件なら、タイトル・パンくずの文字bigramで保険検索します

実在タイトルの合流を最大2件に抑えているのは、4枠すべてを機械的に埋めてしまうと、
質問全体を見たLLMの判断を使う余地が無くなるからです。残り2枠以上は必ず残します。

**この2件をどの順で埋めるかも決めてあります。** `実在タイトル → 型番 → リンク`の順です。

順番が問題になるのは、上限が2件だからです。ある経路が発火しやすくなると、
他の経路の候補を押し出してしまいます。実際、リンク検索の発火条件に「どこ」を足したとき、
「合宿で39代はどこに行きましたか」で`メインページ`が先に入り、
**正解の`合宿`が押し出されました**（M24）。質問に実在ページ名がそのまま含まれる一致は、
本文のスコア計算より信頼できるので、先に採ります。

**リンク検索**は、資料の在り処を尋ねる質問だけ、本文中のリンクまで直接照合します。
目次のリード文には全節を載せられないため、メインページ後半にある「過去問」のリンクは
索引にあってもページ選択から落ちていました。発火条件は
`リンク / URL / https? / github / drive / 資料…場所 / どこ / ありか`です。

**型番の扱い**

「TR797とは何ですか？」に「資料内に記載なし」と誤答したことがあります。
資料には`TR-797`と書かれており、ハイフンの有無だけで引けなくなっていました（M8）。
これは意味の推論ではなく、決定的な正規化で解ける問題です。

- 英字で始まり数字を含む4文字以上だけを、型番候補にします
- 大文字小文字、ハイフン、アンダースコアの差を無視します
- ページ本文の完全一致上位2件を、モデル候補より先に加えます
- 節選択でも、完全一致した節を優先して統合します

**節の選択**

- 選択本文が12,000字以内なら、全節を渡します
- 超える場合だけ、モデルで最大8節へ絞ります
- モデルが返したIDは、選択済みページに実在するものだけを受け付けます

## アシスタントの参照範囲

アシスタントは誰でも作れるので、「この範囲だけ見てね」という指示を
モデルのお願いベースにすると成り立ちません。**範囲の除外はコードで行います。**

- 正本
  - 検証: `backend/internal/assistant/assistant.go`
  - 除外: `backend/internal/pipeline/pipeline.go`の`inScope`と`scopedTOC`
  - 解決: `backend/internal/server/server.go`の`lookupAssistant`

参照範囲は、**狭める指定だけ**を持てます。広げる指定はありません。

- 出所: Wiki / 公式サイト
- 区分: 許可リスト内の1区分

そして、ページ選択、実在タイトル候補、保険検索、型番検索の**すべての経路で**
範囲外を落とします。どれか1つでも漏れると、範囲指定が意味を失うためです。

**公式サイト限定のとき**

- 全体目次ではなく`SiteTOC`を渡します
- 限定目次が作れなければ、全体目次へ広げるのではなく、目次なしにします

「作れなかったから全体を渡す」としてしまうと、範囲指定が静かに破られます。

**アシスタントIDの取得に失敗したとき**

- 汎用へ戻して続行しません
- 質問回数を消費する前に、409で停止します

利用者は特定のアシスタントを選んだつもりなので、勝手に汎用で答えるのは誤りです。

**出典**

- 選択済みの索引から、サーバーが組み立てます
- SSEの`pages`イベントで送り、モデルの文章から抽出しません

モデルに出典一覧を作らせると、「引き継ぎWiki」「公式サイト」といった
実在しない出典名を生成できてしまいます。サーバーだけで組み立てれば、この経路を閉じられます。

**本文中の出典（2026-08-11に追加）**

回答の文末に、根拠の資料を小さなチップで出しています。ここで気をつけたのは、
**この仕組みで上の保証を崩さないこと**です。

- モデルへ渡す資料には、ページの並び順で`資料番号`を振ります（1始まり）
- モデルが書けるのは`[1]`という**番号だけ**です。題名もURLも書かせません
- 画面が`[n]`を`pages`イベントのn件目へ解決します
- **範囲外の番号は消します。** 文字として残すと、モデルが作った`[9]`が本文に残ります
- 出典が0件のときは何もしません（番号付きの箇条書きを壊さないため）

つまりモデルの出力は「何番目か」に閉じており、表示される題名とURLは
これまでどおりサーバーが索引から組み立てたものです。実在しない出典名を
書ける経路は増えていません。

正本は`backend/internal/pipeline/pipeline.go`の`sourceNumber`と、
`web/src/markdown.tsx`の`citationChips`です。

**参照（どこを開けば確かめられるか）**

出典カードはページ単位ですが、36,261字ある「駆動・フレーム班」のようなページでは、
どこを読めばよいか分かりません。そこで回答の末尾に、**実際に読んだ節のパンくず**を
出しています。

- `Source.Sections`に、索引の`Chunk.Breadcrumb`（「ページ名 ＞ 見出し」）を入れます
- 節が確定するのは絞り込みの後なので、**`pages`イベントは2回流れます**
  - 1回目: 参照中の資料（節はまだ空）
  - 2回目: 節を入れた確定版
- 節が取れなかった資料はページ名で代替します。空欄を出すより、
  少なくともどのページかは分かるほうがよいためです

## アシスタント保存値

アシスタントとして保存できる値の上限です。

- 名前: 1〜40文字
- 説明: 最大120文字
- 指示: 1〜1,500文字
- ID: 小文字英数字とハイフンで、最大64文字
- アイコン
  - PNG / JPEG / WebPのdata URIだけ
  - 最大96KiB
  - SVGと外部URLは拒否します（SVGはスクリプトを含められるためです）

権限は次のとおりです。

- 作成: ログイン済みの全員
- 閲覧: ログイン済みの全員
- 編集・削除: 作成者本人、主管理者、共同管理者
- 他人のものは読み取り専用で閲覧でき、変更するときは複製する
- ID、作成者、作成日時は、編集で変更しません

削除権限を両管理者にも与えているのは、偉い人だから、ではありません。
**明らかなゴミを片付けるための最小限の権限**として置いています（2026-08-08に人間が判断）。
2026-08-11から主管理者は共同管理者を追加・解除でき、両管理者は運用管理画面にも入れますが、
アシスタント内容を事前審査しない方針と、削除権限を広げない方針は変えていません。

## API入力と履歴

外部から受け取る値の上限です。正本は`backend/internal/server/server.go`です。

**質問**

- JSON本文で送ります。URLへは入れません（サーバーログに質問文が残るためです）
- 1〜500文字
- リクエスト本文は最大32KiB

**回答モード**

- `auto / fast / standard / deep`だけを受け付けます
- 空文字は、旧画面との互換のため`auto`とみなします
- 通常画面で選べるのは`auto / deep`だけです。`fast / standard`は自動判定と旧画面の互換用です

**会話文脈**

- 最大2往復
- 各質問は1〜500文字
- 各回答は1〜2,000文字
- 過去の回答を、今回の根拠としては扱いません

**履歴**

- 利用者ごとに最大30チャット
- 保存リクエストは最大1MiB
- 上限を超えたら、更新日時が古い履歴から削除します

**アシスタント保存リクエスト**

- 最大256KiB

## 回答モードの決定

`auto`のとき、どの段階を使うかをコードで決めています。
正本は`backend/internal/pipeline/pipeline.go`の`resolveResponseMode`です。

分類のためにLLMをもう1回呼ぶ、ということはしていません。それをすると
毎回の費用と待ち時間が増えるからです。

- 利用者が明示した場合は、その段階を使います
- 自動の場合は、質問に含まれる語で決めます
  - 比較、差異、変遷、歴代、全体、網羅、理由、背景などは`deep`
  - 型番、いつ、何年、誰は`fast`
  - その他は`standard`

モデルの選択にも制限があります。

- サーバー環境変数の許可リストだけを使います
- 未設定の段階は、既定モデルへ戻します
- **実測で改善を確認するまで、強いモデルを既定にしません**

## 変更時の確認

この文書の内容を変えるときは、次の順番で進めてください。

いきなりコードを直して「良くなった気がする」で終わらせると、
何が直って何が壊れたのか分からなくなります。

1. 先に、再現できる失敗例を用意します
2. 実データにevidence（根拠）が存在することを照合します
3. Python測定経路とGo本番経路の共通規則を、両方更新します
4. 数字を`docs/08-測定記録.md`へ残します
5. 次のコマンドを実行します

```bash
python eval/retrieval_eval.py

cd backend
GOCACHE=/private/tmp/wasa-go-cache go test ./...
```
