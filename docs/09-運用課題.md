## A. 保守者が一人であること

このプロジェクトの構成上いちばん重いのがここです。技術的な難しさではなく、
**引き継ぎが1回でも失敗すると復旧できない**という形の課題です。

### A-1. クラウドの所有権を次の代へ渡す手順が無い

[07-デプロイと更新.md](07-デプロイと更新.md)は「ゼロから作る手順」としては完成していますが、
**すでに動いている本番を別の人へ移す手順**がありません。移すものは次の4つです。

- Google Cloudプロジェクト（Cloud Run / Firestore / Cloud Storage / Secret Manager / Artifact Registry）
- Cloudflare Pages
- 請求先アカウント
- GitHubリポジトリ

作り直せることと引き継げることは違います。Firestoreには共有アシスタントと
利用者フィードバックが入っているので、**作り直しでは失われるものがあります。**

着手の条件: 代替わりの予定が立った時点。または保守者が1人から2人になった時点。

### A-2. 請求の主体が個人のまま

無料枠を超えたときに誰へ請求が行くのか、代が替わるときにどう付け替えるのかが
決まっていません。金額そのものより、**支払いが止まった瞬間にサービスも止まる**
（A-3と同じ性質の非対称性）ことが問題です。

着手の条件: A-1と同時。サークルとして支払う形にするかどうかは技術判断ではないので、
[CONTRIBUTING.md](../CONTRIBUTING.md)の「人間に確認してほしいこと」と同じ扱いにします。

### A-3. 課金を外すと止まるが、外さないと無料枠から出る

M23で一度踏んでいます。原因はプリペイド残高ではなく、プロジェクトの請求階層が
「無料トライアル」だったことでした。いまは次の形で回避しています。

- 課金を紐づけない`wasa-chat`プロジェクトの無料枠キーをGeminiに使う
- **本番GCPプロジェクトからは課金を外さない**（Cloud RunとFirestoreに必要）

つまり**2つのプロジェクトに依存していて、片方は課金あり、片方は課金なし**という
状態です。引き継ぎのときにこれを1つにまとめようとすると、どちらかが壊れます。

なお、本番Secret Managerのキーとローカルのキーは別物で、
**どちらのプロジェクトのキーかが未確認**のまま残っています（F-7）。
管理画面のGemini残量は本番Goが試みた送信だけを数えるため、評価スクリプトが同じ
プロジェクトの枠を使うと実残量より多く見えます。正確な運用には本番と評価の
Geminiプロジェクトを分ける必要があります。

着手の条件: すぐ。確認するだけで済み、分からないまま引き継ぐと調べ直しが重いためです。

### A-4. `eval/golden.json` の引き継ぎ経路が無い

ゴールデンデータは設問に実データの引用を含むため、リポジトリへコミットしていません
（`eval/golden.example.json`だけが公開されています）。

**これが失われると、精度の回帰測定ができなくなります。** 33問は実際の誤答から
組み立てたもので、作り直すには同じだけの測定をやり直すことになります。

着手の条件: すぐ。渡し方（保守者間で直接渡す、非公開の置き場を決める、など）を
決めて[00-引き継ぎガイド.md](00-引き継ぎガイド.md)へ書けば終わります。

### A-6. 更新確認に主管理者の個人アカウントを使っている（2026-09-12）

自動更新のCloud Run Jobは、いま**主管理者の個人Wikiアカウント**でログインしています。
docs/07 は「読み取り専用の更新確認用アカウントを使い、主管理者の個人アカウントとは
分ける」としており、**いまはその方針を満たしていません。**

そのままだと、代替わりのときに前任者のアカウントを止めた瞬間に自動更新が止まります。
しかも**止まったことに気づく手段がありません**（B-1と同じ）。

さらに、このパスワードは2026-09-12にチャットへ貼られた経緯があるため、
**変更したほうがよい**状態です。

着手の条件: すぐ。Wikiに読み取り専用アカウントを作り、
`wasa-wiki-update-user` / `wasa-wiki-update-pass` を差し替えるだけです。

### A-7. Discordを足したことで、失効の手段が2か所になった（2026-09-13）

Discordのスラッシュコマンドは**Wikiアカウントを見ません**。誰が使えるかは
Discordのサーバー参加者で決まります。

つまり退部者を止めるには、**Wikiのアカウントを止めるだけでは足りず、
Discordサーバーからも外す**必要があります。いままで「Wiki側で止めれば終わり」
だったものが、2か所を揃え続ける約束になりました。

一人保守だと、この種の約束は片方が忘れられます（docs/09 A）。

⚠️ **これはPMが承認した運用です**（2026-09-13）。「WASAのDiscordにいる人＝部員」
という前提が実態として正しい、という判断に乗っています。前提が崩れたとき
（招待リンクの流出、OBの残留、外部の人の参加）に効いてきます。

着手の条件: 代替わりのとき。**引き継ぎ資料に「失効はWikiとDiscordの両方」と
書くところまでが1組**です。

### A-8. Discordの会話ログを読むため、本番にBOTトークンを置くことになった（2026-09-13）

`/要約` と `/todo` は、チャンネルの直近の発言を読んでから要約します。過去ログの
取得（`GET /channels/{id}/messages`）は**BOTトークンでしか認証できません**。

当初は「BOTトークンは登録スクリプトでしか使わない。回答の書き換えは対話ごとの
トークン（15分で失効）が認証を兼ねるので、本番に置かなくてよい。置かなければ
漏れない」という設計でした。**この方針は撤回しました**（2026-09-13にPMが判断）。

影響:

- `DISCORD_BOT_TOKEN` は Secret Manager 経由でのみ渡すこと。`--set-env-vars`で
  直接書かない（[07-デプロイと更新.md](07-デプロイと更新.md) §5.5）
- 漏れると、**そのボットの権限でできることは全部できます**。回答の書き換えだけ
  だった頃より影響範囲が広い
- **質問だけなら不要です。** 要約を使わない運用にするなら置かなくてよく、その場合
  `/要約`・`/todo` は「設定されていません」と返して何もしません

着手の条件: トークンが漏れた疑いがあるとき。Discord開発者ポータルで再生成し、
Secret Managerへ新しい版を入れて再デプロイします。

### A-9. チャンネルの会話をGeminiへ送ることの承認（2026-09-13）

`/要約` と `/todo` は、**そのチャンネルで喋った全員の発言**を無料枠へ送ります。
コマンドを打った人だけの話ではありません。

⚠️ **2026-09-13にPMが承認済みです。** [D-1](#d-1-無料枠への送信の承認はその時点の代のもの)
と同じ性質の承認で、**その代のPMのもの**です。代が替わったら再確認してください。

いま守っていること:

- 範囲は**日数で指定**する（既定7日・最大365日）。1コマンドで集めるのは最大5000件、
  Discordへのリクエストは最大120回
- 読む先は**補完の候補から選ぶ**（公開チャンネル全部／個別の公開チャンネル）。
  ⚠️ 候補は文字列オプションなので**手でIDを打つこともできる**。打ったチャンネル以外を
  読むときは、公開チャンネルかどうかを実行前に確かめている（`discord.PublicChannel`）
- 横断は**公開チャンネルだけ**。⚠️ ボットが見えるチャンネルと、コマンドを打った人が
  見えるチャンネルは**同じではない**。ボットを幹部用の非公開チャンネルへ入れていると、
  1年生が横断要約を打っただけで本来読めない内容が流れる。`@everyone` から見える
  チャンネルに限れば、**打った人が自分で開けば読めたもの**しか混ざらない
- 回答の先頭に「公開チャンネル5件の過去30日ぶん・812件の発言（12人）を読みました」と
  書く。**何が送られたかがチャンネルに残る文言そのもので分かる**ようにしている
- ボットの発言は送らない（WASA自身の回答を要約し直さないため）

⚠️ **公開チャンネルの判定はDiscordの権限上書きを見ているだけである。** ロールごとの
細かい可視性までは計算していない。非公開にしたいチャンネルは、`@everyone` から
「チャンネルを見る」を外してあることを確認してください。

着手の条件: 導入時に部内へ一言告知すること。「WASA botは要約コマンドを打った
ときだけ直近ログを読む」と伝えておけば、あとは普通の運用で回ります。

### A-10. 共有ドライブの閲覧境界は、DriveのACLではなく「WASA Chat側の許可」（2026-09-13）

`ingest/dump_drive.py` はサービスアカウントで共有ドライブを読み、`origin="drive"` として
**全員が同じ索引を引く**形で取り込みます。利用者ごとのOAuthはしません。

⚠️ **その結果、Driveのファイル別権限は索引へ入れた時点で失われます。**

代わりに、**WASA Chat側で許可制にしています**（PMの指示、2026-09-13）。

- 設定画面に共有ドライブは出ますが、許可されていない人には
  「管理者の許可が要ります」と表示され、トグルが出ません
- 許可は管理画面の「利用者・権限」から出します。管理者はもとから使えます
- ⚠️ **サーバー側でも弾きます**（`Server.mayUseDrive`）。画面が古くても、
  `tools: ["drive"]` を直接送られても、許可が無ければ読みません

つまり閲覧境界は「**WASA Chatで共有ドライブを許可された人か**」です。
ログインできる全員ではありません。

守ること:

- 取り込むのは `DRIVE_FOLDER_IDS` で明示したフォルダだけ。検索で見える全ファイルではない
- ⚠️ **フォルダの中に「許可した人にも見せたくない資料」を置かないこと。**
  許可の粒度は利用者単位で、**ファイル単位ではありません**
- 可能なら個人所有の共有フォルダではなく**共有ドライブ**を使う。所有者が退部しても消えない
- 鍵（JSON）は作らない。Cloud Run Jobs のサービスIDで呼ぶ。鍵が無ければ漏れない
- 退部時は**管理画面の許可も外す**（Wikiアカウントを止めるだけでは、許可の行が残る）

着手の条件: 導入時。フォルダの中身を一度人の目で確認してください。技術で判断できません。

### A-11. Discordのバックグラウンド処理は保証されていない（2026-09-13）

`/wasa` は「考えています」を返したあと、goroutine で回答を作ります。Cloud Run は
既定でリクエスト処理中しかCPUを割り当てないため、**この処理は保証されていません**
（`cpu-throttling` は未設定＝ON、`min-instances=0`）。

⚠️ **ただし実機では正常に動いています**（2026-09-13に確認）。いま直す根拠はありません。
「測ってから足す」に従い、**壊れたときの直し方だけ記録しておきます**。

直し方: `--no-cpu-throttling` は使わないこと（試算で月¥2,000〜2,500。「API以外は¥0」と
両立しない）。deferを返す**前に** Cloud Tasks へ登録し、Cloud Run の内部エンドポイントを
別リクエストとして実行します。Cloud Tasks は月100万回まで無料です。

着手の条件: `/wasa` が「考えています」のまま止まる報告が出たとき。

### A-12. 画面からのDiscord検索は、Discordの権限と無関係な人に見える（2026-09-13）

設定画面でDiscordのサーバーと連携すると、質問に関係する会話を検索して回答の材料に
します（`GET /guilds/{id}/messages/search`）。

⚠️ **検索APIは「ボットが見える範囲」で認可されます。** 一方、画面の利用者は
Wikiアカウントで、**Discordに入っていない人も含みます**。そのまま使うと、
Discordのメンバーでない人が非公開チャンネルの中身を読めます。

守っていること:

- 検索時に**チャンネルIDを明示**して渡す（省略するとボットが見える全範囲が対象になる）
- 渡すのは `@everyone` から見える公開チャンネルだけ
- 返ってきたヒットも、許可したチャンネル以外は捨てる（二重の防御）
- `DISCORD_SEARCH_CHANNELS` を設定すると、さらにそのチャンネルだけへ絞れる

⚠️ **公開チャンネルの判定は `@everyone` の `VIEW_CHANNEL` 拒否を見ているだけで、
ロールごとの上書きまでは計算していません**（docs/09 の公開判定と同じ）。
Codexは「画面からの検索は許可リストで明示すべき」と強く勧めています。
心配なら `DISCORD_SEARCH_CHANNELS` を設定してください。

⚠️ **2026-09-13に、WASA42代のサーバーは非公開チャンネルが0件になりました**
（PMが権限を変更）。つまりこのサーバーでは「公開チャンネルだけ」という絞り込みが
**何も除外していません**。WASA Chatにログインできる人は、Discordの全チャンネルの
内容へ到達できます。

これはPMの判断で、引き継ぎとして価値の高い「議事録」「荷重試験」を読めるように
するためです。前提が変わったとき（外部の人がWikiアカウントを持つ、限定公開に
したいチャンネルができる）に効いてきます。

⚠️ **利用者ごとの連携（2026-09-14）は、権限ではなく絞り込みです。** どのサーバーを
読むかを利用者が設定画面で選べるようになりましたが、これは**自分の連携先を決める**
ものであって、**他人から隠す**ものではありません。ボットが入っているサーバーは
全利用者の「連携できるサーバー」に名前が出て、誰でも連携できます。上の閲覧境界
（ログインできる人 = 公開チャンネルを読める人）は変わっていません。画面にもそう書いています。

⚠️ **ボットの追加も、管理者に限っていません。** 招待URLは設定画面から誰でも開けます。
歯止めはDiscord側にあり、**追加先のサーバーで「サーバー管理」権限を持つ人しか追加できません**。
つまり「自分が管理している代のサーバーへ入れる」ことはできますが、他人のサーバーには入れられません。
そのぶん、**入れた瞬間からそのサーバーの公開チャンネルが全利用者の検索対象になり得ます**。

着手の条件: 部内に「Discordには入っていないがWASA Chatは使う人」がいると分かったとき、
または非公開にしたいチャンネルができたとき。後者は `DISCORD_SEARCH_CHANNELS` で
読む先を明示するのが早いです。ボットを入れられる人を絞りたくなったときは、
招待URLを管理画面だけに戻すか、`DISCORD_GUILD_IDS` で連携先を許可制にできます。

### A-13. カレンダーは許可制にしていない（2026-09-13）

共有ドライブは管理者の許可が要りますが、**カレンダーは要りません**。Discordと
同じ扱いで、ログインできる人なら誰でも設定画面からつなげます。

理由は、部の予定は全員が知ってよいもので、許可制にすると「次のTFはいつ？」に
ほとんどの部員が答えられなくなるためです。

⚠️ **そのぶん、何を読ませるかの設定が境界になります。**

- `CALENDAR_IDS` に **`primary` を指定しないこと。** 指定すると、そのアカウントの
  私的な予定まで読めます
- 部の予定表（`xxxxx@group.calendar.google.com`）だけを指定する
- 予定の説明欄に、部員に見せたくないことを書かない（120字まで読みます）

着手の条件: 予定表に見せたくない予定が入ると分かったとき。共有ドライブと同じ
許可制に乗せ替えられます（`Server.mayUseDrive` と同じ形）。

### A-5. 主管理者の変更だけは再デプロイが要る

日常的な担当追加は、主管理者が管理画面から共同管理者を付与できるようになりました。
共同管理者はFirestoreへ保存するため再デプロイは不要です。一方、全員を誤解除しても
復旧できるよう、主管理者だけはCloud Runの`ADMIN_USERS`で決めます。

さらに、**Wikiの利用者名には空白が入る**ため、`--set-env-vars`の区切り文字を
`^;^`で変えないと利用者名が途中で切れます。このとき
**誰も管理者にならないまま、エラーも出さずに静かに起動します**
（[07-デプロイと更新.md](07-デプロイと更新.md)に警告あり）。

主管理者そのものを交代するときだけ`gcloud run services update`が必要です。
新しい主管理者を先に追加し、その人が入れることを確認してから前任者を外してください。

## B. 壊れても気づけない経路

「壊れること」より「**壊れたことに誰も気づかないこと**」が問題な項目です。

### B-1. 監視とアラート（2026-09-13に設定済み）

**`/health` の外形監視を入れました。**

| | |
|---|---|
| 監視 | Cloud Monitoring 稼働時間チェック「WASA Chat /health」 |
| 間隔 | 5分（3地点から） |
| 判定 | **2xx 以外を異常**とみなす |
| アラート | 「WASA Chat が応答しない」→ メール通知 |
| 鳴る条件 | **10分続けて失敗したとき**。直ったら30分で自動的に閉じる |

⚠️ **1回の失敗では鳴らしません。** `min-instances=0` なので、ゼロスケールからの
起動待ちで1回だけ落ちることがあります。そこで鳴らすと誤報だらけになり、
そのうち誰も見なくなります。

⚠️ **2xx 以外を異常にしているのが要点です。** 「つながるか」だけを見ると、
索引の読み直しに失敗して 503 を返している状態（B-2）を見逃します。

作り直すときは `tools/setup-uptime-check.sh` を使ってください。
`gcloud` の alpha/beta を入れていない環境でも動くよう、通知先とアラートは
REST API を直接叩いています。

残っている穴: **Cloud Run のエラーログは誰も見ていません。** `/health` が 200 を
返していても、個々の質問が失敗している状態は検知できません。

### B-2. 索引が読めないと起動しないが、起動失敗に気づけない

`INDEX_GCS`が読めないとサーバーは起動しません。**これは意図的で正しい設計**です
（古い索引で黙って動き続けるほうが分かりにくい壊れ方をするため）。

起動しなかったことは、**B-1の外形監視で検知できるようになりました**（2026-09-13）。
`/health` は索引の読み直しに失敗すると 503 を返し、10分続けばメールが飛びます。

### B-3. Wikiが落ちるとログインできない

認証はWikiの`action=clientlogin`へ中継しているので、
**さくらインターネット側の障害がそのまま全機能停止**になります。

これは認証方式の帰結であり、[01-設計方針.md](01-設計方針.md)で選んだ形です。
回避策を入れる（キャッシュした認証を一定時間許す等）ことはできますが、
**認証方式そのものの変更は人間の判断が要る領域**なので、勝手に変えないでください。

着手の条件: 実際に障害で使えなかった日が出たとき。それまでは
「Wikiが見られないときはWASA Chatも使えない」と案内するだけで足ります。

### B-4. 更新確認の管理画面移行は完了

保守者のMacに置いたlaunchdへの依存をなくすため、管理画面からCloud Runへ更新確認を
依頼できるようにしました。Wikiは改訂番号、公式サイトはサイトマップの最終更新日だけを
現行索引と比較するため、本文の再取得より軽く、誤編集を自動反映することもありません。

読み取り専用WikiアカウントはSecret Managerから渡し、本番の管理画面から確認できる状態です。
Mac固有のlaunchdラッパーは削除し、必要時に使える`ingest/check_updates.py`だけを残します。

## C. 混雑と枠（未測定）

### C-1. 何人まで耐えるかを測っていない

現在の設定は次のとおりです。

| 設定 | 値 | 理由 |
|---|---|---|
| `max-instances` | 1 | Geminiへの送信間隔と停止状態をプロセス内で管理しているため |
| `concurrency` | 20 | — |

`max-instances=1`は**増やしてはいけません。** 2台以上にすると、
それぞれが独立にGeminiへ送信してレート制限の管理が壊れます。
増やすなら先に送信間隔の管理を外へ出す必要があります。

着手の条件: 実利用で「遅い」「使えない」の報告が出たとき。
測るときは、F-5「所要時間を分析する」で保存している段階別所要時間を使います。

着手の条件: 実際に上限へ当たったとき。当たっていない段階で文言を作り込むのは

## D. データとプライバシー

### D-1. 無料枠への送信の承認は、その時点の代のもの

非公開Wiki本文をGeminiの無料枠へ送ることは、**2026-08-08のWASA会議で
代表・PMが承認済み**です。`GEMINI_FREE_TIER_APPROVED=true`がその印です。

問題は、この承認が**その代の代表・PMのもの**であることです。
代が替わったときに再承認が要るのかが決まっていません。

着手の条件: 代替わりのとき。承認が要るかどうかは技術判断ではないので、
**勝手に決めず、必ず人間に確認してください。**

### D-2. `SESSION_SECRET` を変えると利用者のデータが失われる

変更すると全員がログアウトするだけでなく、**HMAC利用者キーも変わります。**
その結果、当日の使用回数とチャット履歴が参照できなくなります。

つまり現状、**鍵が漏れても気軽には替えられません。**

着手の条件: すぐ着手する必要はありませんが、
「替えると何が失われるか」を[04-バックエンド.md](04-バックエンド.md)へ
書いておくだけでも価値があります。漏洩時に判断する時間が減ります。

### D-3. 書き出したフィードバックの置き場所

`go run ./cmd/export-feedback`でJSONL／CSVへ書き出しますが、
**生データには非公開Wikiの内容が含まれます**（質問文と回答本文）。

リポジトリへコミットしないことは決まっていますが、
**どこへ置くか・いつ消すか**は決まっていません。

着手の条件: 最初に書き出すとき。

### D-4. 利用者自身が質問文へ書いた個人情報

マスキングは索引を作るときに掛かるもので、**利用者の入力には掛かりません。**
質問文に個人名や連絡先を書いた場合、Firestoreの履歴（最新30件）に残ります。

フィードバックの保存期間は1年、履歴は最新30件という方針は決定済みです
（2026-08-09に人間が判断、`web/public/support.html`にも記載）。

着手の条件: 実際にそういう質問が来たとき。ただし
**マスキングの範囲を変えるのは人間の判断が要る領域**です。

### D-5. アシスタントの参照範囲を緩めない

アシスタントは全員が作れて審査もしませんが、代わりに構造で縛っています
（範囲は狭める指定のみ、出典は索引から組み立ててモデルに触らせない、など）。

特に**「広報（ネタ）」は参照範囲が公式サイトのみ**で、
非公開Wikiが公開ツイートへ混ざる経路を構造的に塞いでいます。**ここを緩めないこと。**

着手の条件: なし。**これは課題ではなく、守るべき制約としてここに書いています。**
