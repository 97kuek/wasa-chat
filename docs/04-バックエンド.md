# WASA Chat バックエンド

> 引き継ぎ資料 04（全10文書）— 認証、API、保存、利用制限を担うサーバー<br>
> [前: 03-プロンプト](03-プロンプト.md)｜[次: 05-フロントエンド](05-フロントエンド.md)

バックエンド（`backend/`）が担う、認証とデータの扱いをまとめたドキュメントです。

わかりやすくざっくり言うと、**ログイン処理やログイン後の
ユーザーごとの扱いがどのようになっているのかをまとめたもの**です。

WASA Chatは非公開Wikiの中身を扱います。誰でも見られるアプリにするわけにはいきませんし、
かといって新しいパスワードを全員に配るのも現実的ではありません。
そのあたりをどう解決したかも、あわせて書いていきます。

なお、なぜその方式を選んだかという判断の根拠は[01-設計方針.md](01-設計方針.md)、
本番での実際の作業手順は[07-デプロイと更新.md](07-デプロイと更新.md)にあります。

## 認証方式

まず初めに、認証方式から説明します。

WASA Chatは、**独自のアカウントを持っていません。** ログインに使うのは、
普段WASA Wikiで使っている利用者名とパスワードです。

こうしている理由は3つあります。

- 新しいパスワードを配らなくて済むこと
- 退部した人はWiki側でアカウントを止めれば自動的に締め出せること
- 誰が使ったかが分かるので利用者ごとに回数制限をかけられる
- 管理者も共有パスワードではなく、操作した本人の名前で監査できる

ことです。

### 認証の流れ

まず初めに、ログイン画面でユーザーはwikiで使用する「利用者名」と「パスワード」を入力します。

受け取った情報をWikiへそのまま渡して、Wikiに「この人は本物ですか」と聞きに行きます。

具体的には以下のような流れでバックエンドで認証を行なっています。

1. MediaWikiからログイントークンを取得します
2.  同じHTTPセッションで`action=clientlogin`へ中継します
3. `status: PASS`の場合だけ成功とします
4. Wikiが返した、正規化済みの利用者名を使います

また、wikiとの認証処理は20秒で打ち切りという設定になっています。

## パスワード

この方式にはある代償があります。

それは**WASA Chatが、Wikiのパスワードを一度受け取る中継点になる**という点です。

つまり、部外秘のデータを閲覧できるwikiのパスワードをこのWASA chatが経由しているということです。

そこで、次の扱いを絶対の前提としています。

- 保存しない
- ログへ出さない
- Wikiへの検証が終わったら、保持しない
- Cookie、Firestore、チャット履歴へ入れない
- ログインの成否にかかわらず、フロントの入力欄から消す

実装は`backend/internal/wiki/auth.go`と`backend/internal/server/server.go`にあります。

ここを変更するときは、上の5つが崩れていないか必ず確認してください。

## セッションCookie

一度ログインしたら、毎回パスワードを入れ直さなくて済むようにしています。

そのために発行するのがセッションCookieです。中に入れているのは利用者名と有効期限だけで、
パスワードは入っていません。改ざんされないよう署名を付けています。

```
- 名前: `wasa_session`
- 内容
  - Base64URL化した利用者名
  - 有効期限
  - `SESSION_SECRET`を使ったHMAC-SHA256署名
- 有効期間: 30日
- 属性
  - `HttpOnly`
  - `Secure`
  - `SameSite=None`
  - `Partitioned`
  - `Path=/`
  ```

`SameSite=None`になっているのは、フロントエンド（Cloudflare Pages）と
バックエンド（Cloud Run）が別のドメインにあるためです。この設定にはHTTPSが必須になります。

**ログアウトしたとき**

- Cookieを失効させます
- 画面上の履歴を消します
- ただし、Firestoreに同期済みの履歴は削除しません（再ログインで復元されます）

**`SESSION_SECRET`の注意**

これは地味に重要なので強調しておきます。

- 本番では、32文字以上の固定値を必須にします
- 変更すると、全員がログアウトします
- さらに、Firestoreの利用者キーも変わるため、**既存の利用回数と履歴を参照できなくなります**

つまり、気軽に変えてよい値ではありません。

## 認証が必要なAPI

どのAPIにログインが要るかの一覧です。

**認証不要**

- `POST /api/login`
- `POST /api/logout`
- `GET /api/session`
- `GET /health`

**認証必須**

- `PUT /api/profile/icon`
- `GET /api/settings`
- `PUT /api/settings`
- `POST /api/ask`
- `GET /api/chats`
- `PUT /api/chats/{id}`
- `DELETE /api/chats/{id}`
- `POST /api/feedback`
- `GET /api/assistants`
- `POST /api/assistants`
- `PUT /api/assistants/{id}`
- `DELETE /api/assistants/{id}`

**管理者ロール必須**

- `GET /api/admin/overview`
- `POST /api/admin/source-check`

**主管理者（`ADMIN_USERS`）必須**

- `POST /api/admin/roles`

`ADMIN_USERS`は画面から外せない主管理者です。主管理者だけが、ログイン実績のある個人の
Wiki利用者を共同管理者へ追加・解除できます。共同管理者はFirestoreの`admin_roles`へ保存し、
権限変更を監査ログへ残します。共同管理者は別の管理者を増減できません。画面を隠すだけでなく、
Go APIがCookieの利用者名と両ロールを毎回照合し、一般利用者には403を返します。

`/api/settings`は**利用者ごとの外部サービス連携**です（2026-09-14に入力欄の「+」から移しました）。
共有ドライブ・カレンダーはオン・オフ、Discordは**連携したサーバーの一覧**を持ちます。

⚠️ **`POST /api/ask`は参照先を受け取りません。** 画面から送らせると、設定を変えた直後の質問が
古い指定のまま飛びます。サーバーが`users/{利用者HMAC}`から読み、使ってよいかを毎回判定します
（共有ドライブの許可は管理者が外せるため、保存された希望をそのまま信じません）。

Discordで連携できるのは`discord.MaxSearchGuilds`（3）サーバーまでで、ボットが入っていない
サーバーIDは保存時に断ります。`GET /api/settings?refresh=1`は、ボットを入れた直後に
サーバー一覧（10分キャッシュ）を取り直すための口です。

更新確認は、索引に保存済みのWiki改訂番号・公式サイト更新日を公開元と比較します。
Wikiの確認用アカウントは`WIKI_UPDATE_USER` / `WIKI_UPDATE_PASS`で指定し、本文の再取得、
索引の再構築、本番反映は行いません。結果は`system_state/source_check`へ保存します。

## CORS・CSRF・セキュリティヘッダー

フロントとバックが別ドメインにあるため、ブラウザ側の制限をきちんと設定する必要があります。

ここで注意が要るのは、**CORSヘッダーを返すだけではCSRF対策にならない**という点です。
Cookieが`SameSite=None`なので、悪意のあるサイトからでもCookie付きのPOSTが飛んできます。
そのため、許可していないOrigin自体を拒否しています。

- Cloud Runでは`ALLOW_ORIGIN`を必須にします（未設定なら起動しません）
- 複数の許可元はカンマ区切りにします
- 許可外Originからの状態変更リクエストは、403で拒否します
- 許可元にだけ次を返します
  - `Access-Control-Allow-Origin`
  - `Access-Control-Allow-Credentials: true`
- ローカル開発時だけ、localhost系ホストを同一扱いにします

セキュリティヘッダーは次のとおりです。

- `X-Frame-Options: DENY`
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: no-referrer`
- CSPで、外部スクリプト、`object`、フレーム埋め込み、外部画像を拒否します

## Firestore保存構造

利用回数や履歴は、Google CloudのFirestoreへ保存しています。

ここで気をつけているのは、**履歴と利用回数のパスへ利用者名を入れない**ことです。
利用者プロフィールには実名と任意の利用者画像を明示して保存しますが、最終利用から1年で消し、
消えた後の履歴・利用回数をHMACから実名へ戻せないようにします。

**利用者キー**

- 利用者名を平文のドキュメントIDにしません
- 固定の`SESSION_SECRET`で`state|利用者名`をHMAC-SHA256化したものを使います

**利用者プロフィール**

- `users/{利用者HMAC}`
- Wiki利用者名、初回利用、最終利用と、本人が設定した場合だけ利用者画像を保存します
- 利用者画像はPNG・JPEG・WebPの中央正方形へ縮小し、96KiB以下のdata URIとして保存します
- `PUT /api/profile/icon`はCookieの利用者だけを更新対象にし、本文から他人の利用者キーを指定できません
- 管理画面で実名と利用回数を結び付けるために使い、質問・回答は入れません
- 最終利用から1年を過ぎた親ドキュメントを管理画面取得時に自動削除します
- 子の履歴・利用回数はHMAC配下のままで、親を消すと実名との対応が失われます
- 外部サービス連携（`tools` / `discord_guilds`）も**同じドキュメント**へ入れます。
  別の入れ物にすると、退部時に利用者を消しても連携設定だけが残ります

**利用回数**

- `users/{利用者HMAC}/usage/{日本時間の日付}`
- `used`と更新時刻を保存します
- 管理画面で30日集計を出すため90日保持し、管理画面取得時に古い日付を自動削除します

**チャット履歴**

- `users/{利用者HMAC}/chats/{chatId}`
- 最大30件
- 質問、回答、出典、回答モード、回答時のアシスタントID・名前、段階別所要時間を含みます

**共有アシスタント**

- `assistants/{assistantId}`
- 全員で共有するため、`users`配下へは置きません
- 作成者名は、責任の表示に必要なので平文で保存・表示します
- ログイン済みの利用者には指示と参照範囲を含む設定を返し、画面で確認・コピーできるようにします
- 同時に`canEdit`を返し、作成者本人と管理者だけが更新・削除APIを使えることはサーバー側でも検査します

**利用者フィードバック**

- `feedback/{feedbackId}`
- **保存期間は1年です。** 新しい報告が保存されるたびに、`submitted_at`が
  1年より古いものをサーバーが削除します（1回あたり最大100件）
  - 定期実行の仕組みを別に持たない方針なので、保存処理のついでに消しています。
    管理者の手作業に頼ると、プライバシーポリシーに書いた期間が守られません
  - 実装は`backend/internal/server/server.go`の`handleSaveFeedback`と、
    `state.Store`の`PurgeFeedback`です
- 報告者は、利用者名ではなくHMACキーで保存します
- 回答評価には、質問・回答・出典・段階別所要時間を含みます
- 画面全体の報告には、質問・回答を含めません
- 管理画面にはフィードバック詳細を出しません
- 開発者用JSONL／CSVにも、報告者の利用者名とHMACキーを出しません

**利用監査ログ**

- `usage_events/{eventId}`
- 利用者HMAC、日時、成否、回答モード、アシスタントID、画像有無、所要時間を保存します
- 質問・回答・画像・出典本文は保存しません
- 保存期間は90日で、管理画面取得時に期限切れを自動削除します

**管理者監査ログ**

- `admin_audits/{auditId}`
- 管理者名、操作、対象、日時を保存します
- 管理画面の閲覧、管理者としてのログイン、他人のアシスタント削除を記録します
- 保存期間は1年です

**Gemini実リクエスト数**

- `api_usage/{太平洋時間の日付}/models/{モデルのハッシュ}`
- 1質問を1回とは数えず、ページ選択・節選択・回答生成と再試行をそれぞれ1回として数えます
- `GEMINI_RPD_LIMIT`（既定500）との差を、管理画面で「推定残り」と表示します
- 別のAPIキーや評価スクリプトが同じプロジェクトを使った分は含まれないため、
  正確にするなら本番用Googleプロジェクトを評価用から分けます

**ブラウザからの接続**

- Firestoreへ直接接続しません
- Wiki認証済みCookieを検証するGo APIだけを通します

## 利用回数

API費用が青天井にならないよう、利用者ごとに1日の質問数を制限しています。

これは単なる節約ではなく、**請求事故を防ぐための安全弁**です。

- 既定は、利用者1人あたり日本時間で1日30質問です
- `DAILY_LIMIT`で変更できます
- Firestoreのトランザクションで、質問の前に1回分を確保します
- 同時送信、別端末、Cookie削除、Cloud Run再起動でも、上限を共有します

Cookieではなくサーバー側で数えているので、ブラウザのデータを消してもリセットされません。

ただし、こちら側の都合で失敗したときにまで回数を減らすのは不公平なので、
次の場合は確保した分を返却します。

- Geminiの利用制限
- LLM通信障害
- 回答生成失敗

なお、アシスタントの取得失敗や不正な入力は、回数を確保する前に止めています。

## 管理画面

プロフィールメニューの「管理画面」から`/admin`を開きます。モデル、APIキー、
全体・個人の上限を変更する機能は持ちませんが、主管理者は共同管理者を追加・解除できます。

表示するものは次のとおりです。

- 今日の質問数、利用者数、個人別の今日・7日・30日の質問回数
- 全利用者の実名検索・各列ソート、共同管理者の追加・解除
- Wiki・公式サイトの変更確認（本文取得、索引再構築、本番反映はしない）
- Geminiのモデル別実リクエスト数、設定上限との差、リセット時刻
- 日次上限、短時間制限と再開予定
- 障害調査用のモデル名、保存先、Cloud Runリビジョン
- 資料更新の進捗、コードと索引のバージョン
- 質問本文を含まない利用監査ログ、管理者監査ログ

索引バージョンは`index.json`と`toc.md`を連結して求めた
SHA-256の先頭12桁で、本文を管理APIへ返さずに読み込んだ内容を照合できます。

GeminiのRPDは太平洋時間、利用者ごとの30回制限は日本時間でリセットされます。
同じ「今日」でも境界が違うため、管理画面はリセット日時を日本時間へ変換して明示します。

## LLMへ送るデータ

非公開Wikiの内容を外部のAIへ送っている以上、何を送っていて何を送っていないかは
はっきりさせておく必要があります。

**送るもの**

- `facts.md`を含む目次
- 選択したWiki・公開資料の本文
- 現在の質問
- 最大2往復の直近会話
- 選択した共有アシスタントの指示
- 利用者が添えた画像（**回答段だけ**。詳しくは次節）

**送らないもの**

- Wikiのパスワード
- Firestoreの全履歴
- 利用者名を含むセッションCookie
- `.env`

**Gemini無料枠について**

無料枠は、送信内容がGoogleの製品改善に使われる可能性があります。
非公開Wikiの本文を送る以上、これは技術判断だけで決めてよい話ではありません。

- 非公開Wiki本文を送るには、組織としての承認が必要です
- 2026-08-08のWASA会議で、代表・PMが承認しました
- 本番では、`GEMINI_PAID_TIER=true`または`GEMINI_FREE_TIER_APPROVED=true`が
  無ければ起動しません（承認を明示しないと動かない、という形にしてあります）

## 画像の添付（2026-08-10）

質問に画像を1枚まで添えられます。汎用の機能なので、どのアシスタントでも使えます。

きっかけは広報用の「ネタツイ」でした。画像に対して投稿文の候補を出させたい、
という要望です。ただし**仕組みとしては特定の用途に縛っていません。**
今後PDFなども足していくなら、器は共通のほうがよいと判断しました。

### 3段のうち、回答段だけに渡す

回答は3回モデルを呼んでいます。

```
① ページ選択（目次 + 質問）
② 節選択（選んだページの本文 + 質問）
③ 回答生成（節 + 質問 + 画像）   ← 画像はここだけ
```

**①②へは渡しません。** ①は目次からページ名を選ぶ仕事で、画像を見せても
ほとんど働きません。全段へ渡すと、入力の費用が3回ぶん乗るだけになります。

実測では、768×223のJPEGで**入力が1,131トークン**でした（プロンプト込み。
画像そのものは約1,100トークン）。目次が2万トークンを超えているので比率としては
小さいのですが、3倍にする理由はありません。

> 画像の大きさとトークン数の関係は**まだ測れていません。**
> Gemini無料枠の日次上限（500リクエスト）に当たったためです。

### 文章が空でも送れる

「これでツイート作って」のように、**文章より画像のほうが本体**である使い方が
あります。そのため質問文が空でも、画像があれば受け付けます。

### 保存しない

**画像はどこにも保存しません。** Firestoreは1ドキュメント1MBで、履歴は
最大30チャットです。画像を持たせると、数回のやりとりで上限に当たります。

履歴には`hasAttachment`という真偽値だけを残し、画面では「画像を添付」と
表示します。開き直しても画像そのものは出てきません。

### 受け取り方

画面側は**長辺768pxのJPEGへ縮めてから**送ります。768pxなのは、Geminiが画像を
処理するタイルの一辺に合わせているためです。スマホの写真をそのまま送ると
数MBになり、リクエストが通りません。

ただし**画面側の申告は一切信用しません。**

| 検査 | 内容 |
|---|---|
| 枚数 | 1枚まで |
| 大きさ | 復号前にbase64の長さで弾き、復号後に400KBで弾く |
| 形式 | **先頭バイトを見て判定する。** 申告されたMIMEも拡張子も使わない |
| 受け付ける形式 | JPEG・PNG・WebPのみ |

順序に意味があります。**大きさを先に見てから復号します。** 逆にすると、
巨大なbase64を一度メモリへ展開してから捨てることになります。

`/api/ask`の本文上限は、画像1枚が載るよう32KB→1MBへ広げました。

Cookie、HTTP本文、履歴、アシスタント、フィードバックなど、サーバー境界の上限値は
`backend/internal/server/limits.go`へ集約しています。個々のハンドラーへ数値を直接書くと、
同じ制約が別の値へずれても気づきにくいためです。上限を変えるときは、このファイルと
対応する回帰テストを一緒に変更してください。

### 画像を読めないモデルでは失敗させる

手元の既定モデル（Ollama / qwen3:30b-a3b）は画像を読めません。ここで黙って
画像を捨てると、**画像を見て答えたつもりの嘘**が返ります。そのため
`ErrImagesUnsupported`で必ず失敗させ、画面には
「いま動いているモデルは画像を読めません」と出します。

このとき利用回数は返却します。利用者の質問の書き方が原因ではないためです。

### 無料枠へ画像を送ることについて

Wiki本文と同じく、**無料枠は送信内容が製品改善に使われる可能性があります。**
部員の顔が写った写真を送る可能性がある以上、本文とは別の判断が要ります。

- 2026-08-10に、この点も承認済みであることを確認しました
- 判断が変わった場合は、この機能を止めるか有料枠へ切り替えてください

## 利用者への説明

ここまでの内容のうち、利用者が知っておくべきことは
`web/public/support.html`（画面の「ヘルプとポリシー」）にまとめてあります。

- 取得する情報と目的、保存期間の一覧
- パスワードを保存しないこと
- 履歴・利用回数の保存先はHMAC化し、管理画面用実名プロフィールは1年で消すこと
- 外部のAIサービスへ何を送り、何を送らないか
- 自分で削除できるもの（履歴・自作アシスタント）と、できないもの（匿名のフィードバック）

**この文書と`support.html`は、同じ事実を2か所に書いています。**
保存期間やマスキング範囲を変えるときは、必ず両方を直してください。
片方だけ直すと、利用者へ嘘の説明をすることになります。

## 確認

認証まわりを直したときは、次を実行してください。

```bash
cd backend
GOCACHE=/private/tmp/wasa-go-cache go test ./...

LIVE_WIKI_TEST=1 GOCACHE=/private/tmp/wasa-go-cache \
  go test ./internal/wiki -run '^TestLoginSuccess$'
```

最後に、この文書の内容を変えるときの注意です。

- 通常のテストは模擬Wikiを使うので、外部へは接続しません
- 実Wikiでテストするときの秘密値は、`.env`だけに置いてください
- **認証方式や個人情報のマスキング範囲を変えるときは、先に人間の判断を得てください。**
  技術的に正しいかどうかとは別に、サークルのデータをどう扱うかという判断が要る部分です
