# WASA Chat デプロイと更新

> 引き継ぎ資料 07（全10文書）— 検証済みの変更を本番へ反映し、戻すための手順<br>
> [前: 06-評価とフィードバック](06-評価とフィードバック.md)｜[次: 08-測定記録](08-測定記録.md)

この文書は、WASA Chatを本番環境で動かすための作業手順です。

手元で動いているものを、部員が実際にリンクを踏んで、使える状態にするまでの作業をデプロイと言います。

**上から順にやれば動く**ように書いてあるので、初めての人はそのまま進めてください。

また、一度作ってしまえば、あとの更新作業は§6の数コマンドだけで済みます。

## 構成

全体像は[全体構成図](images/architecture.svg)を参照してください。
デプロイ先は次の4つだけです。

| 置き場所 | 担当 |
|---|---|
| Cloudflare Pages | `web/`をビルドしたReact画面 |
| Cloud Run（東京） | `backend/`のGo API。Wiki認証、検索、Gemini、管理API |
| Cloud Storage | 非公開の`index.json`と`toc.md` |
| Firestore（東京） | 履歴、利用回数、共有アシスタント、フィードバック、管理データ |

ブラウザはFirestoreやCloud Storageへ直接接続せず、Wiki認証済みのCloud Run APIだけを通します。
索引をDockerイメージへ入れないため、資料だけの更新ではイメージを作り直しません。

索引にはWiki本文が含まれます。Cloud Storageは公開せず、Cloud Runのサービスアカウントだけに
読み取りを許可してください。`.env`、`dump/`、`data/`、`eval/golden.json`は
GitHub、Cloudflare Pages、公開レジストリ、Dockerイメージへ置きません。

## デプロイ前の必須確認

作業を始める前に、次を全部確認してください。

途中まで進めてから足りないものに気づくと、やり直しが面倒な箇所がいくつかあります。

- [ ] `git status`に`.env`、`dump/`、`data/`、`eval/golden.json`が出ていない
- [ ] `data/index.json`と`data/toc.md`を、最新の全資料から手動で再生成した
- [ ] 索引を置くCloud Storageバケットを作り、実行サービスアカウントへ読み取りを許可した
- [ ] `cd backend && go test ./...`が成功する
- [ ] `cd web && npm ci && npm run build`が成功する
- [ ] Cloud Run利用のため、Google Cloudの請求先を設定した
- [ ] Geminiの利用枠を確認した（無料枠への非公開Wiki送信は、2026-08-08のWASA会議で代表・PMが承認済み）
- [ ] Google Cloud Billingの予算アラートを設定した
- [ ] `SESSION_SECRET`を32文字以上の乱数で作成した
- [ ] `ADMIN_USERS`に管理者本人のWiki利用者名を決めた（共有アカウントは使わず、管理画面・アシスタント削除・初期作成者のロールになります）
  - 初期アシスタントが登録されるのは**保存先が空のときだけ**です。以降は画面での編集が正本になります
- [ ] 管理画面の更新確認に使う専用Wikiアカウントを用意し、利用者名とパスワードをSecret Managerへ登録した
- [ ] フィードバックを書き出す開発者がFirestoreを読めることを確認した
- [ ] Firestoreを`asia-northeast1`に作成し、削除保護を有効にした
- [ ] Cloudflare Pagesの本番URLが決まっている

さて、チェックが全て埋まったら次に移りましょう。

## 1. Google Cloudを準備する

最初にGoogle Cloud側の土台を作ります。

以降の例に出てくる次の値は、自分の環境のものに置き換えてください。

- `PROJECT_ID`: Google CloudのプロジェクトID
- `REGION`: `asia-northeast1`
- `REPOSITORY`: `wasa-chat`
- `SERVICE`: `wasa-chat-api`
- `FRONTEND_ORIGIN`: Cloudflare Pagesの本番URL（例: `https://wasa-chat.pages.dev`）

Google Cloud CLIへログインし、プロジェクトを選びます。

```bash
gcloud auth login
gcloud config set project PROJECT_ID
gcloud config set run/region asia-northeast1
```

必要なAPIを有効化します。

```bash
gcloud services enable \
  run.googleapis.com \
  artifactregistry.googleapis.com \
  secretmanager.googleapis.com \
  firestore.googleapis.com \
  aiplatform.googleapis.com
```

FirestoreをCloud Runと同じ東京リージョンに作成します。
別リージョンにすると通信が遅くなるので、必ず揃えてください。

```bash
gcloud firestore databases create \
  --database='(default)' \
  --location=asia-northeast1 \
  --type=firestore-native \
  --delete-protection
```

作成したら、Cloud Runの実行サービスアカウントへ、Firestoreの読み書き権限
`roles/datastore.user`を付与します。

なお、ブラウザ用のFirebase SDKやFirestore Security Rulesからは接続しません。
Cloud Runのサービスアカウントだけを使います。

最後に、Dockerイメージ用の非公開リポジトリを作ります。

```bash
gcloud artifacts repositories create wasa-chat \
  --repository-format=docker \
  --location=asia-northeast1 \
  --description="WASA Chat本番イメージ"

gcloud auth configure-docker asia-northeast1-docker.pkg.dev
```

最後に、索引を置くバケットを作ります。**Wikiの本文がそのまま入るので、
公開アクセスは必ず禁止してください。**

```bash
gcloud storage buckets create gs://wasa-chat-index \
  --location=asia-northeast1 \
  --uniform-bucket-level-access \
  --public-access-prevention

gcloud storage buckets add-iam-policy-binding gs://wasa-chat-index \
  --member=serviceAccount:SERVICE_ACCOUNT \
  --role=roles/storage.objectViewer
```

読み取りだけを許可しています。差し替えは手元から`gcloud`で行うので、
サーバーに書き込み権限を持たせる理由がありません。

## 2. シークレットを登録する

パスワードやAPIキーは、コードにも環境変数にも直接書かず、Secret Managerへ置きます。

まず、セッション署名鍵を生成します。

```bash
openssl rand -base64 48
```

登録するのは次の2つです。

- 上で生成した出力を`wasa-session-secret`として登録
- Gemini APIキーを`wasa-gemini-api-key`として登録
- 更新確認専用Wikiアカウントの利用者名を`wasa-wiki-update-user`、パスワードを`wasa-wiki-update-pass`として登録

**登録はGoogle Cloud Consoleからをおすすめします。** コマンドで登録すると、
シェルのコマンド履歴に秘密の値がそのまま残ってしまうためです。

Wikiの利用者名とパスワードは登録しません。ログイン時に各利用者が入力し、
バックエンドがWikiへ中継する仕組みなので、本番サーバーへ固定のWikiパスワードを
置く必要がないからです。

**内部の段階別モデル**

- 既定では、全段階で`gemini-3.5-flash-lite`を使います
- 比較測定で改善を確認した場合だけ、`GEMINI_FAST_MODEL`、`GEMINI_STANDARD_MODEL`、
  `GEMINI_DEEP_MODEL`をCloud Runの環境変数へ追加します
- ブラウザからモデルIDは指定させません

## 3. Dockerイメージを作って送る

アプリをDockerイメージにまとめて、Artifact Registryへ送ります。

Apple Silicon（M1以降のMac）で作業している場合の注意があります。**そのまま作ると
Macの形式になってしまい、Cloud Runで動きません。** `linux/amd64`を明示してください。

また、タグにはGitのコミットIDを使います。あとから「本番はどのコードか」を追跡できるようにするためです。

```bash
IMAGE=asia-northeast1-docker.pkg.dev/PROJECT_ID/wasa-chat/wasa-chat-api:$(git rev-parse --short HEAD)
docker buildx build --platform linux/amd64 --load -t "$IMAGE" .
docker push "$IMAGE"
```

Docker Desktopを使えない場合は、同じDockerfileをGoogle Cloud Buildで実行できます。

```bash
gcloud builds submit --tag "$IMAGE" .
```

ただしCloud Buildを使うときは、送信されるファイルに注意が要ります。

- `.gcloudignore`が`.env`、`dump/`、評価データを除外し、本番に必要な
  `data/index.json`と`data/toc.md`だけをCloud Buildへ送ります
- 実行前に`gcloud meta list-files-for-upload`で、秘密ファイルが含まれていないことを確認してください
- Cloud Buildを実行する利用者には、ビルド作成権限が必要です。**APIを有効にしただけでは足りません**
- 権限を追加できない場合は迂回せず、Docker Desktopを起動して上の`docker buildx build`を使ってください

なお、`data/index.json`と`data/toc.md`もイメージに入りますが、
本番では`INDEX_GCS`が優先されるため使われません。手元と`docker compose`のための
控えです。それでも中身はWiki本文なので、**Artifact Registryは公開設定にしないでください。**

## 4. Cloud Runへデプロイする

作ったイメージをCloud Runへデプロイします。

```bash
gcloud run deploy wasa-chat-api \
  --image "$IMAGE" \
  --region asia-northeast1 \
  --allow-unauthenticated \
  --min-instances 0 \
  --max-instances 1 \
  --concurrency 20 \
  --cpu 1 \
  --memory 1Gi \
  --timeout 300 \
  --set-env-vars "^;^LLM_PROVIDER=gemini;GEMINI_FREE_TIER_APPROVED=true;GEMINI_RPD_LIMIT=500;INDEX_GCS=gs://wasa-chat-index;APP_VERSION=COMMIT_ID;DAILY_LIMIT=30;FIRESTORE_PROJECT_ID=PROJECT_ID;ALLOW_ORIGIN=FRONTEND_ORIGIN;ADMIN_USERS=42 Wasa Taro" \
  --set-secrets "SESSION_SECRET=wasa-session-secret:latest,GEMINI_API_KEY=wasa-gemini-api-key:latest,WIKI_UPDATE_USER=wasa-wiki-update-user:latest,WIKI_UPDATE_PASS=wasa-wiki-update-pass:latest"
```

⚠️ **`--set-env-vars`の先頭にある`^;^`を消さないでください。**

見慣れない記号なので消したくなりますが、これは設定同士の区切り文字を
カンマからセミコロンへ変える指定です。消すと次の問題が起きます。

`ADMIN_USERS`は複数人ならカンマ区切りなので、カンマを設定同士の区切りには使えません。
`GEMINI_RPD_LIMIT`は管理画面の推定残量に使う表示上の上限です。AI Studioで
プロジェクト・モデルの上限が変わったときだけ、同じ値へ直してください。
`WIKI_UPDATE_USER`と`WIKI_UPDATE_PASS`は、管理画面からの読み取り専用更新確認に使います。
個人の主管理者アカウントとは分け、Secret Manager以外へ値を残さないでください。
`APP_VERSION`には`git rev-parse --short HEAD`の結果を入れます。Cloudflare Pagesが自動で
埋め込むコミットと照合し、画面だけ先に更新された状態を管理画面から検知するためです。

さらに厄介なのが、**Wikiの利用者名には空白が入る**ことです（例: `42 Wasa Taro`）。
既定のカンマ区切りのままだと利用者名が途中で分割され、
**誰も管理者にならないまま、エラーも出さずに静かに起動します。**

各オプションの意味は次のとおりです。

- `--allow-unauthenticated`
  - APIそのものを、ネットワーク的に到達可能にする設定です
  - アプリ内では、Wikiアカウントによるログインを引き続き必須にしています
- `min-instances=0`
  - 未使用時のCloud Run費用を抑えます。`1`にすると無料枠を確実に超えます
- `max-instances=1`
  - Geminiへの送信間隔と停止状態を、現在はプロセス内で管理しているためです。
    2台以上にすると、それぞれが独立に送信してしまいます
- `ALLOW_ORIGIN`
  - パスを含めず、Cloudflare PagesのOriginだけを指定します
  - プレビュー環境も認証付きAPIへ接続する場合は、カンマ区切りで追加します
- `INDEX_GCS`
  - 索引の置き場所です。設定するとイメージ内の`data/`ではなくこちらを読みます
  - **読めなければ起動しません。** 古い索引で黙って動き続けるほうが分かりにくいためです
- `GEMINI_FREE_TIER_APPROVED=true`
  - 2026-08-08のWASA会議で、代表・PMが非公開Wiki本文の無料枠への送信を許可したことを示します
  - 将来有料枠へ切り替えた場合は、確認のうえ`GEMINI_PAID_TIER=true`を使います

デプロイが終わったら、API URLを取得します。

```bash
gcloud run services describe wasa-chat-api \
  --region asia-northeast1 \
  --format='value(status.url)'
```

`https://...run.app/health`が200を返すことを確認してください。
なお、Cloud Runでは末尾が`z`の一部パスがプラットフォーム側で処理されるため、
`/healthz`は使っていません。

## 5. Cloudflare Pagesへデプロイする

次に画面側を公開します。

- Cloudflare Dashboardで`Workers & Pages` → `Create` → `Pages` → `Connect to Git`を選びます
- GitHubのWASA Chatリポジトリを選びます

ビルド設定は次のとおりです。

- Production branch: `main`
- Root directory: `web`
- Build command: `npm run build`
- Build output directory: `dist`

環境変数は次の3つです。

- `NODE_VERSION`: `24`
- `VITE_API_ORIGIN`: 手順4で取得したCloud RunのURL
- `VITE_WIKI_URL`: WASA WikiのURL

ここで**順番の都合による作業が1つ**あります。Cloud Runの`ALLOW_ORIGIN`には
Pagesのアドレスが必要ですが、そのアドレスはPagesを作らないと分かりません。
そのため、Pages URLが発行されてからCloud Run側を更新します。

```bash
gcloud run services update wasa-chat-api \
  --region asia-northeast1 \
  --update-env-vars "ALLOW_ORIGIN=https://発行された名前.pages.dev"
```

そのうえでCloudflare Pagesを再デプロイし、ブラウザで次を確認してください。

- Wikiの利用者名とパスワードでログインできる
- 「許可されていない送信元です」が出ない
- 質問、進捗表示、Markdown、TeX、参照資料が表示される
- 再ログイン後も、当日の残り回数が維持される
- 別端末でログインしても、当日の残り回数とチャット履歴が一致する
- ログアウト後は画面から履歴が消え、再ログインするとFirestoreから復元される

## 5.5 Discordのスラッシュコマンド（2026-09-13）

Discordから使えるようにします。**回答はチャンネル全員に見えます。**

| コマンド | 何をするか | 索引 | 出典 | BOTトークン |
|---|---|---|---|---|
| `/wasa <質問> [アシスタント]` | 引き継ぎ資料に質問する | 読む | 付く | 不要 |
| `/要約 [期間] [範囲]` | 最近の会話を要約する | 読まない | 無し | **要る** |
| `/todo [期間] [範囲]` | 最近の会話からToDoを抜き出す | 読まない | 無し | **要る** |

`期間`は日数（既定7日・**最大365日**）。`範囲`は**打つと候補が絞られます**
（「公開チャンネル全部」＋そのサーバーの公開チャンネル）。どちらも省略できます。

⚠️ **範囲の補完（autocomplete）は、打つたびにCloud Runへ問い合わせが来ます。**
Discordは3秒しか待たず、「考えています」で先延ばしできません。サーバー側は
チャンネル一覧を1分だけ覚えて間に合わせています（`discord.channelCacheTTL`）。

`アシスタント`も打つと候補が絞られます。指定すると、そのアシスタントの口調・参照
範囲の上に**Discord向けの書き方を重ねます**。画面と同じものをそのまま使うと、
表やMermaidを書いてきて崩れるためです。

**Discordが描画する記法**: `### `見出し、`-# `小さい文字、`**太字**`、`__下線__`、
`- `箇条書き（入れ子は半角スペース2つ）、`1. `番号付き、`> `引用、`[文字](URL)`。

**描画しない記法**: 表、Mermaid、そして **`- [ ]` のタスクリスト**（`[ ]` が文字の
まま出ます）。ToDoは `☐` を使い、モデルが `- [ ]` と書いてもサーバー側で
`- ☐` へ直します（`discord.fixCheckboxes`）。回答に付く資料番号 `[1]` も、
Discordには押す先が無いのでサーバー側で外します（`discord.stripCitations`）。

⚠️ **サブコマンド（`/wasa 要約`）にはしていません。** Discordは「サブコマンドを
持つコマンド」に普通のオプションを混ぜられないため、そうすると質問のときも
`/wasa 質問 <text>` と打つ必要が出ます。**普段の質問を一番短く打てること**を
優先して、別コマンドとして登録しています（2026-09-13にPMが判断）。

⚠️ **要約は回答パイプラインに載せていません。** 回答プロンプトには「WASA固有の
事実を資料外で補わない」「文末に [1] を付ける」という規則が入っており、会話の
要約をそこへ流すと、**会話に出てくる人名・日程はすべて「資料外」**なので
「記載なし」と返るか、存在しない資料番号を作ります。索引を読まない別経路
（`internal/recap`）にしてあります。

⚠️ **常時接続のボットにはしません。** メンションを受け取るにはGateway
（WebSocketの常時接続）が要り、`min-instances=0` が使えなくなります。
1か月は約259万秒、Cloud Runの無料枠は月18万vCPU秒なので、**無料枠がカバーするのは
約7%だけ**です。しかもGatewayは心拍を返し続けるためCPUを常に割り当てる必要があり、
月8,000円規模になります。「API以外は¥0」（docs/01 §7）と両立しません。

スラッシュコマンドはDiscordが**呼ばれたときだけ**HTTPでPOSTしてくるので、
いまのゼロスケールのまま動きます。

**手順**

1. Discord Developer Portal でアプリを作る
2. 「Interactions Endpoint URL」へ `https://<Cloud RunのURL>/api/discord` を入れる
   - ⚠️ **先にCloud Runへ公開鍵を設定しておくこと。** Discordは登録時に
     わざと壊した署名を送ってきて、401を返せるかを試します
3. Cloud Runへ設定を入れる

```bash
gcloud run services update wasa-chat-api --region asia-northeast1 \
  --update-env-vars "DISCORD_PUBLIC_KEY=<Public Key>,DISCORD_APP_ID=<Application ID>"
```

4. コマンドを登録する（1回だけ）

```bash
DISCORD_APP_ID=... DISCORD_BOT_TOKEN=... DISCORD_GUILD_ID=... \
  sh tools/register-discord-command.sh
```

5. `/要約`・`/todo` を使うなら、BOTトークンを本番へ置く

```bash
printf '%s' "<BOT Token>" | gcloud secrets create wasa-discord-bot-token --data-file=-
gcloud run services update wasa-chat-api --region asia-northeast1 \
  --update-secrets "DISCORD_BOT_TOKEN=wasa-discord-bot-token:latest"
```

Discordの「Bot」設定で、**メッセージ履歴を読む**権限を与え、要約を使いたい
チャンネルにアプリを入れてください。

⚠️ **当初は「BOTトークンを本番へ置かない」方針でした。** 回答の書き換えは対話
ごとのトークン（15分で失効）が認証を兼ねるので不要だったためです。過去ログの
取得（`GET /channels/{id}/messages`）だけはBOTトークンでしか認証できないため、
要約機能を入れる判断とともに**撤回しました**（docs/09 A-8）。`--set-env-vars` で
直接書かず、必ず Secret Manager 経由にしてください。

**質問だけなら置かなくてよい**設計です。未設定なら `/要約`・`/todo` は
「設定されていません」と返して、何も読みません。

**守っていること**

- 署名（Ed25519）を検証しないリクエストは処理しません。この口は公開されるので、
  検証を外すと誰でも叩けて無料枠を消費させられます
- 出典は**サーバーが索引から組み立てて**添えます。画面のカードと同じ保証で、
  モデルが書けるのは資料番号だけです（docs/02）
- 2000字を超えるときは**切り詰めず、続きを別メッセージで送ります**（最大3通）。
  出典URLは日本語タイトルのパーセントエンコードで最長214文字あり、4件付くと
  本文に440字しか残らず、長い回答が毎回途中で切れていました（2026-09-13に索引で確認）。
  3通でも収まらないときだけ本文を削り、**出典は最後まで残します**
- 文字数は**UTF-16の符号単位**で数えます。Discordの数え方に合わせないと、
  絵文字が入った回答が境界で弾かれます
- 失敗や操作ミス（回数切れ・権限不足・コマンド違い）は、「考えています」を消してから
  **本人だけに見える形**（ephemeral）で伝えます。チャンネル全員に見せる必要がありません
- 同じチャンネル・同じ人の**直前3往復**を覚えていて、続けて聞けます。
  画面の履歴とは別枠です
- 横断では**動いている公開スレッド**も読みます。`GET /guilds/{id}/channels` は
  スレッドを返さないため、班ごとにスレッドで話していると1件も入りませんでした。
  非公開スレッドと、非公開チャンネル配下のスレッドは読みません
- Discordが429を返したら `Retry-After` に従って**1回だけ**待ち直します
- 質問文に `@everyone` が入っていても通知は波及しません
- 利用回数はDiscordの利用者ごとに数えます（Wikiの利用者とは別枠）。要約も1回ぶん使います
- 要約は**読む前に権限を確かめ**、読めないチャンネルなら回数を減らしません
- `/wasa この会話を要約して` と打たれたら、送信せずに `/要約` へ案内します
  （質問として流すと索引に無いので「記載なし」と返ってしまうため）

**要約で守っていること**

- ⚠️ **横断するのは公開チャンネルだけです。** ボットが見えるチャンネルと、コマンドを
  打った人が見えるチャンネルは**同じではありません**。ボットを幹部用の非公開チャンネルへ
  入れていると、1年生が横断要約を打っただけで本来読めない内容が流れます。
  `@everyone` から見えるチャンネルに限れば、**打った人が自分で開けば読めたもの**しか
  混ざりません（`discord.Channel.public`）
- 回答の先頭に「公開チャンネル5件の過去30日ぶん・812件の発言（12人）を読みました」と
  書きます。**何が送られたかがチャンネルに残る文言そのもので分かります**
- 1コマンドで集めるのは最大5000件・Discordへのリクエストは最大120回。
  日数を1年まで指定できるぶん、実質の歯止めはこちらです
- ⚠️ **候補に出したものだけが選ばれるとは限りません。** `範囲`は文字列オプション
  なので、候補に無いチャンネルIDを手で打てます。打ったチャンネル以外を読むときは、
  **公開チャンネルかどうかを実行前に必ず確かめます**（`discord.PublicChannel`）
- ボットの発言は送りません（WASA自身の回答を要約し直さないため）
- 会話ログは部員が自由に書いた文字列なので、「これまでの指示を無視して」のような文が
  混ざり得ます。**ログは要約の対象であって従う対象ではない**とsystem側で明示しています
- ⚠️ **長いログでも古いほうを捨てません。** 6万字を超えたら分割し、塊ごとに
  「決まったこと・出た案・やること」を取りこぼさず拾ってから、最後に1回まとめます
  （最大7回の呼び出し）。直近だけを見る作りにすると、**前の代で出た案が黙って消えます**

⚠️ **チャンネルの会話をGeminiへ送ることは、2026-09-13にPMが承認済みです。**
影響を受けるのはコマンドを打った人だけではなく、そのチャンネルで喋った全員です。
docs/09 D-1 と同じ性質の承認なので、**代が替わったら再確認**してください（docs/09 A-9）。

⚠️ **誰が使えるかはDiscordのサーバー参加者で決まります。** Wikiアカウントでは
ないので、退部者を止めるには**Discord側から外す**必要があります。失効の手段が
2か所になります（docs/09 A-7）。2026-09-13にPMが承認した運用です。

## 6. 更新とロールバック

一度動き出したあとの、日常的な更新作業です。

更新には2種類あります。**どちらなのかで、必要な手順がまったく違います。**

| 変えたもの | やること | かかる時間 |
|---|---|---|
| 資料だけ（Wiki・公式サイト・ガイドの内容） | `sh tools/publish-index.sh` | 1分程度 |
| コード（Go・React・プロンプト） | イメージを作り直してデプロイ | 10分程度 |

**資料の更新は自動で回る（2026-09-12）**

公開元の変更を検知して索引を作り直すところまで、Cloud Run Job が自動で行います。
手で動かす必要があるのは、**取り込む範囲を変えたときだけ**です。

```bash
# 手元で確かめるとき
python tools/auto_update.py --check-only   # 変更の有無だけ見る（取得しない）
python tools/auto_update.py                # 変更があれば取り込んで差し替える
```

⚠️ **止める条件を持っています。** 誤編集は受け入れましたが、**取得の失敗まで
受け入れたわけではありません。** 次のときは差し替えません。

- ページ数が100件を下回る
- どれかの出所のページ数が、いまの版から3割以上減っている
- チャンクが1つも無い

取得が途中で落ちた索引を上げると、全部の質問へ「資料が見つかりません」と答え続ける
状態になり、しかも壊れていることが画面から分かりません。

**Cloud Run Job の作り方**

⚠️ **先にWikiの資格情報をSecret Managerへ入れてください。** 読み取り専用の
更新確認用アカウントを使い、主管理者の個人アカウントとは分けます。

```bash
printf '%s' '更新確認用の利用者名' | gcloud secrets create wasa-wiki-update-user --data-file=-
printf '%s' 'そのパスワード'       | gcloud secrets create wasa-wiki-update-pass --data-file=-

# 更新Jobだけが読めるようにする
for name in wasa-wiki-update-user wasa-wiki-update-pass; do
  gcloud secrets add-iam-policy-binding "$name" \
    --member="serviceAccount:wasa-chat-updater@PROJECT_ID.iam.gserviceaccount.com" \
    --role=roles/secretmanager.secretAccessor
done
```

**サービスアカウントは分けてあります。** アプリ（`wasa-chat-runner`）は索引を
**読むだけ**で、書き込めるのは更新Job（`wasa-chat-updater`）だけです。
同じアカウントを使い回すと、アプリ側の穴から索引を書き換えられる経路ができます。

```bash
IMAGE=asia-northeast1-docker.pkg.dev/PROJECT_ID/wasa-chat/wasa-chat-updater:$(git rev-parse --short HEAD)
docker buildx build --platform linux/amd64 -f Dockerfile.updater --load -t "$IMAGE" .
docker push "$IMAGE"

gcloud run jobs deploy wasa-chat-updater \
  --image "$IMAGE" \
  --region asia-northeast1 \
  --max-retries 1 \
  --task-timeout 30m \
  --memory 1Gi \
  --set-env-vars "INDEX_GCS=gs://wasa-chat-index,WIKI_API=https://wasabirdman.sakura.ne.jp/wbwiki/w/api.php" \
  --service-account wasa-chat-updater@PROJECT_ID.iam.gserviceaccount.com \
  --set-secrets "WIKI_USER=wasa-wiki-update-user:latest,WIKI_PASS=wasa-wiki-update-pass:latest"
```

**定期実行（Cloud Scheduler）**

```bash
gcloud scheduler jobs create http wasa-chat-updater \
  --location asia-northeast1 \
  --schedule "0 * * * *" \
  --time-zone "Asia/Tokyo" \
  --uri "https://asia-northeast1-run.googleapis.com/apis/run.googleapis.com/v1/namespaces/PROJECT_ID/jobs/wasa-chat-updater:run" \
  --http-method POST \
  --oauth-service-account-email SERVICE_ACCOUNT
```

⚠️ **間隔を短くしすぎないこと。** 変更が無ければ数秒で終わりますが、変更が
あると**取得だけで10分以上かかります**（`dump_wiki.py` の1秒間隔は縮めない）。
1時間ごとで足ります。

**資料だけを手で更新する場合**

索引（`data/index.json`と`data/toc.md`）はCloud Storageの`gs://wasa-chat-index`に
置いてあり、サーバーは起動時にそこから読みます。**イメージには入っていません。**
そのため資料の更新では、ファイルを差し替えるだけで済みます。

```bash
python check_updates.py        # 必要なら手元でも変化を確認する
python rebuild.py              # 取得・索引作成・検索検査
sh tools/publish-index.sh      # 差し替えて本番へ反映
```

`publish-index.sh`は、上げる前に**ページ数が100件を下回っていないか確認します。**
取得が途中で失敗した索引を本番へ上げると、全部の質問に
「資料が見つかりません」と答え続ける状態になり、しかも壊れていることが
画面から分からないためです。

**差し替えたら、それで反映されます（2026-09-12に変更）。**
動いているインスタンスは `INDEX_WATCH_SECONDS`（既定60秒）ごとにCloud Storageの
世代番号を見ていて、変わっていれば**再デプロイせずに読み直します**。

以前はここで環境変数を1つ動かし、新しいリビジョンへ入れ替えていました。
**資料を直してから反映されるまでの待ちは、その手順が作っていました。**

確認は世代番号だけを見るので1リクエストで済み、変わっていなければ3.4MBは読みません。
`min-instances=0` なので使われていない間はこの確認ごと止まりますが、次のアクセスで
起動したインスタンスは最新を読むため、取りこぼしは起きません。

**コードを変えた場合**

1. `main`を最新にします
2. テストを通します（`go test ./...` と `npm run build`）
3. 新しいコミットIDのDockerタグをpushします
4. Cloud Runを新しいイメージへ更新します

**なぜ索引をイメージから外したのか**

以前は`data/index.json`をDockerイメージへ焼き込んでいました。動きはしますが、
**資料を1文字直すだけでもイメージの再ビルドとpushとデプロイが必要**でした。
資料の更新はコードの更新より頻繁に起きるので、重い方の手順に引きずられていました。

いまは`INDEX_GCS`が設定されていればそちらを正本とし、**読めなければ起動を止めます。**
イメージに焼いた古い索引で黙って動き続けると、「更新したのに反映されない」という
一番分かりにくい壊れ方をするためです。`INDEX_GCS`が無ければ`DATA_DIR`の
ファイルを読むので、手元と`docker compose`はこれまでどおり動きます。

保管しているのは3.4MBなので、費用は月1円に届きません。

**なぜ完全自動にしないのか（2026-09-12に一部を撤回）**

理由は2つありました。

- 非公開Wikiの認証情報と取得データを、外部のCIサービスへ置かないため
- Wikiの誤編集が、そのまま自動で本番の回答に反映される事故を避けるため

⚠️ **2つ目は、2026-09-12に人間の判断で受け入れることにしました。**
誤編集がそのまま回答へ出るリスクより、更新が遅れることのほうが困るという判断です。
この文書に残しておくのは、**あとから「なぜ自動なのか」を調べる人のため**です。
覆すときは、この判断ごと見直してください。

1つ目は変えていません。**外部のCIサービスは使いません。**
自動化するなら、既存のGoogle Cloudの中（Cloud Run Job）で動かし、
Wikiの資格情報はいまと同じSecret Managerから読みます。

**管理画面からの更新確認（2026-08-11に移行）**

管理画面の「更新を確認」は、Cloud RunからWikiの改訂番号と公式サイトのサイトマップを
現在の索引と比較します。本文の取得、索引の再構築、公開は行わないため、変更が出たときだけ
従来どおり`python rebuild.py`以降を人が実行します。結果と実行者はFirestoreへ残ります。

以前のMac用launchdラッパーは、管理画面からの本番確認後に削除しました。
読み取り専用のCLIが必要な場合は`python check_updates.py`を直接実行できます。

**ロールバック**

- Cloud Runのリビジョン一覧から、直前の正常なリビジョンへトラフィックを戻します
- Artifact Registryの古い正常イメージは、すぐに削除しないでください（戻し先が無くなります）

**シークレットの更新**

- Gemini APIキーは、Secret Managerで新しいバージョンを作ります
- `SESSION_SECRET`を変えると全員がログアウトします。さらにHMAC利用者キーも変わるため、
  **既存の利用回数と履歴を参照できなくなります**

## 7. 運用上の注意

最後に、運用していて実際に遭遇する事柄をまとめます。

**Geminiの429は「遅くなるだけ」ではありません**

- 短時間の上限なら、指定時間後の再試行で回復する場合があります
- しかし日次の上限だと、リセットまで生成できません
- WASA Chatは、待機理由と再開見込みを画面へ表示します

**利用者単位の30回制限**

- HMAC化した利用者キー、日本時間の日付、使用回数をFirestoreへ保持します
- Firestoreのトランザクションで確保するため、Cloud Runの再起動、Cookie削除、
  別端末のいずれでもリセットされません

**チャット履歴**

- 質問・回答・出典を含むため、Firestoreの権限をCloud Run実行サービスアカウント以外へ広げません
- 利用者ごとに新しい30件だけを保持し、個別削除はFirestoreにも反映します

**フィードバック**

- 回答評価には質問・回答・出典が含まれるため、書き出しを担当する開発者以外へ
  Firestoreの読み取り権限を広げません
- 管理画面とメール通知は持たず、開発者がApplication Default Credentialsで直接書き出します
- 報告者の利用者名は保存せず、HMACキーも書き出しません
- JSONL／CSVの書き出し手順は[06-評価とフィードバック.md](06-評価とフィードバック.md)を参照します

**Geminiのプロジェクト全体の制限**

- 現在は、1インスタンス内で送信間隔を制御しています
- `max-instances`を2以上にする前に、共有レート制限用の外部ストアを設計する必要があります
